## What changed

### #626 API key management guide (`docs/api-key-management.md`)

- **Existing:** `POST/GET/PATCH /api/v1/api-keys`, `stk_` keys stored as SHA-256 hashes (raw key returned once), CIDR `allowedIps`, `lastUsedAt`, `x-api-key` via the gateway, `revokedAt` enforced by `apiKeyAuth`.
- **Guide covers:** creating keys, using them, least privilege, zero-downtime rotation (create, deploy, verify via `lastUsedAt`, retire), revocation, a compromised-key response playbook, audit and monitoring, and an error reference.
- **Documented gaps:** there are no permission scopes (a key carries its user's full access) and no revoke endpoint (nothing sets `revokedAt`). The guide gives the least-privilege workaround (dedicated user, one key per integration, IP allowlist), a self-service lock-down via `allowedIps`, and the operator SQL for revocation.

### #627 Dispute timeline data contract (`docs/dispute-timeline-contract.md`)

- **Existing:** `GET /api/disputes/:id/timeline` built by `disputeTimelineService` from the dispute, evidence, appeal, and escrow tables; six event types with a same-timestamp tie-break order.
- **Contract covers:** response envelope, required fields and types, per-type metadata, ordering rules, event sources and cardinality, how on-chain events (`dis_rai`, `dis_res`, `dis_to`, `gov_esc`, `mil_dis`) are or are not indexed, an anomaly table, producer/consumer compatibility rules, and a consumer checklist.
- **Anomalies documented from the code:** the indexer's `dis_res` handler sets the escrow to `Completed` but never sets `disputes.resolved_at`, so disputes resolved only on-chain have no `resolved` event; `dis_to` and `gov_esc` are not indexed; `arbiter_assigned` precedes `filed` because it uses the escrow's creation time.
- **Test:** `backend/tests/disputeTimelineDocs.test.js` builds a dispute where every event shares one timestamp and asserts the service's output order equals the documented event types in documented tie-break order, so adding or re-ranking an event type without updating the doc fails CI.

### #628 Relayer funding runbook (`docs/runbooks/relayer-funding.md`)

- **Existing:** `RELAYER_SECRET_KEY`, network chosen by `STELLAR_NETWORK`, `GET /api/relayer/status` (returns `relayerAddress` and `network`), fees at Horizon p50 plus a 1000 stroop buffer, key rotation in `docs/runbook.md` §3.5.
- **Runbook covers:** finding the relayer and its network, Horizon balance and spend queries, runway-based thresholds per environment, a copy-paste scheduled balance check script, testnet (Friendbot) and production (`stellar tx new payment`, two-person rule) top-ups, alert response for warning, critical, empty-balance, and unconfigured states, and a wrong-network rollback table covering each failure case.
- **Documented gaps:** there is no balance metric, built-in alert, or automatic top-up; the scheduled check is the interim control.
- Linked from `docs/runbook.md` §3.5.

### #630 Admin bulk action safety guide (`docs/admin-bulk-actions.md`)

- **Existing:** `PATCH /api/admin/escrows/bulk-status` behind `adminAuth` + `requireMfa`, max 50 ids, transition table in `lib/escrowTransitions.js`, per-escrow transactions with partial success, one `BULK_ESCROW_STATUS_UPDATE` audit row per update, cache invalidation.
- **Guide covers:** when to use it (database copy only, the contract is the source of truth), permissions, request/response and every error, allowed and blocked transitions, a step-by-step safe procedure, post-action verification, the audit log, and a rollback strategy with a reviewed SQL restore.
- **Documented gaps:** no preview/dry-run mode (the guide uses a pre-change snapshot as the manual preview), the audit row does not record previous status, `performedBy` is always `"admin"` (operators put name and ticket in `reason`), and there is no undo endpoint.
- **Test:** `backend/tests/adminBulkDocs.test.js` parses the documented transition table and asserts it equals the state machine in `escrowTransitions.js` for every status pair.
